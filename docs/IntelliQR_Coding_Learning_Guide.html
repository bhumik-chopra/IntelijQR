Learning rule: Start with one small function and follow its input and output. Do not begin by trying to understand an entire large page such as QrGeneratorPage.tsx.

Five questions to ask when reading any module

  1. What input does it receive?
  2. What output does it return?
  3. Which rule belongs here?

Example mental model: Button

A page should not repeatedly code borders, disabled states, spinners and icon positions. A reusable Button accepts properties such as variant, size, loading and icon. This is the React principle of composition: pages describe intent while the component owns presentation.

Practice: Open Button.tsx. Find its prop interface, default values and conditional class names. Then search <Button to see how many larger features reuse it.

Why types come before pages

For example, QrGeneration describes the data returned by the backend. A hook can promise Promise<QrGeneration>, and the page receives autocomplete and compile-time errors if it uses a missing property.

Schema versus model

A schema describes data entering or leaving the API and can validate it. A model describes application/domain state after loading from MongoDB. Keeping them separate prevents HTTP-specific choices from spreading through business logic.

Exception flow

Service detects missing resource
    → raises NotFoundError
    → main.py exception handler
    → returns safe JSON + HTTP 404 + request ID
Practice: Find one raise NotFoundError in a service, then find its handler in main.py. This teaches exception propagation.

3. How frontend and backend communicate

Shared frontend client

frontend/src/lib/api/client.ts wraps fetch. It prevents every feature from repeating URL construction, JSON headers, cookies, Bearer tokens, error parsing and refresh retry.

Page → feature hook → feature API → apiClient → fetch('/api/v1/...')

Small example

// Feature API describes the request
get(id): Promise<QrGeneration> {
  return apiClient.get(`/qr/generations/${id}`)
}

# Endpoint validates authentication and parameters
@router.get('/{generation_id}')
async def get_generation(...):
    return await service.get_owned(generation_id, current_user.id)

Vercel production rewrite

The browser calls the same Vercel origin. vercel.json forwards /api/:path* to Render. This teaches the difference between an application route, an API route and a reverse proxy/rewrite.

Important: The browser should not receive MongoDB, Blob or Brevo secrets. It communicates only with FastAPI, and FastAPI communicates with those services.

4. Dependency injection: how modules are connected

backend/app/api/dependencies.py is the composition root. It answers: “Which concrete objects does this feature need?”

def get_qr_generator_service(repository, settings):
    return QrGeneratorService(
        repository=repository,
        renderer=QrRenderer(),
        storage=VercelBlobQrStorage(...) or LocalQrStorage(...),
        payload_builder=QrPayloadBuilder(),
        ...
    )

The generator service does not decide how FastAPI creates its repository. It only receives an object with the required operations. This is dependency inversion.

What this design enables

  • Production can use Vercel Blob while local development uses disk.
  • Tests can inject a fake repository or fake Blob client.
  • Business logic is not tied to FastAPI global variables.
  • Features can be changed at the application boundary.
Practice: Trace get_share_vault_service. Write down every dependency it creates and whether it belongs to data, security, storage or analytics.

7. Build a basic QR generator first

Smallest possible idea

text → QR matrix → draw modules → PNG bytes

In IntelliQR, QrPayloadBuilder converts structured form data to a standard string. QrRenderer uses qrcode to create the matrix and Pillow to draw the output.

Modules to read in order

  1. schemas/qr_generation.py — supported requests and rules.
  2. services/qr/payload_builder.py — URL/text/mailto/tel/Wi-Fi/vCard/geo strings.
  3. infrastructure/qr/renderer.py — matrix and image drawing.
  4. services/qr/generator_service.py — complete use case.
  5. endpoints/qr_generations.py — REST interface.
  6. features/qr-generator/api and hook — frontend connection.
  7. QrGeneratorPage.tsx — full UI composition.

Why PayloadBuilder is separate

Creating correct Wi-Fi or vCard text is different from drawing black squares. Separation lets payload syntax be tested without rendering an image.

Practice: Call QrPayloadBuilder().build(TextQrRequest(...)) in a Python shell. Then try Email and Wi-Fi types and observe the standardized strings.

9. Persisting and managing QR records

After rendering, QrGeneratorService.generate stores artifacts and creates a MongoDB record through QrGenerationRepository. The record includes ownership, safe payload preview/details, slug, design, file paths, limits and timestamps.

Why store a preview and hash?

  • Preview lets the Dashboard display safe information.
  • Hash supports identity/deduplication ideas without exposing full sensitive content.
  • Protected destinations use encrypted storage instead of plaintext.

Dashboard module chain

DashboardPage

 → qrGeneratorApi / dashboardApi

Editing a design re-renders and stores replacement files before deleting old storage. This teaches safe replacement ordering: create the new asset first, update the database, then remove the previous asset.

10. Durable QR downloads and storage adapters

Local adapter

LocalQrStorage writes to a configured directory. It is easy for development but unsuitable for free Render persistence.

Cloud adapter

VercelBlobQrStorage saves private objects, reads authenticated bytes and deletes the generated group. Both adapters expose conceptually similar save, read and delete operations.

Download flow

Download button
 → qrGeneratorApi.saveDownload()
 → authenticated GET file endpoint
 → service loads record and reads private Blob
 → FastAPI streams bytes with Content-Disposition
 → browser creates object URL and saves file
Abstraction lesson: The generator service asks storage to save/read/delete. It does not contain Vercel HTTP details. This keeps business logic independent of the vendor.

12. Dynamic QR tracking

Start with a redirect

A dynamic QR encodes {redirect_base_url}/r/{slug}. qr_redirects.py receives a public GET, asks QrGeneratorService.resolve_redirect for the destination and returns HTTP 307.

Add tracking carefully

  1. Find the generation by unique slug.
  2. Check active, expiry and scan limit.
  3. Atomically increment scan count.
  4. Create an analytics event as a background task.
  5. Redirect without caching or referrer leakage.

Why configuration matters

The hostname is permanently encoded in the QR image. INTELLIQR_REDIRECT_BASE_URL must be reachable by phones and spelled exactly. Fixing the environment changes only newly generated images.

Debugging lesson: Never guess what a QR contains. Decode the actual downloaded image, print the embedded URL and test that URL independently.

14. AES-GCM encryption module

The central module is backend/app/core/vault.py. VaultCipher derives a 256-bit key with SHA-256, generates a new 12-byte nonce and uses AESGCM.

nonce = secrets.token_bytes(12)
encrypted = cipher.encrypt(nonce, plaintext, associated_data)
stored = nonce + encrypted

Why associated data differs

  • intelliqr-destination-v1 binds encrypted strings to the destination format.
  • intelliqr-file-v1 binds encrypted bytes to file storage.

Associated data is authenticated but not encrypted. Using distinct labels prevents one ciphertext type from being treated as another.

Module users

UserPurpose
QrGeneratorServiceEncrypt protected destination URLs.
VercelBlobShareStorageEncrypt/decrypt file bytes around Blob operations.
EncryptedShareStorageSame behavior for local files.
dependencies.pyConstructs the cipher with the Vault key or fallback secret.
Cryptography lesson: Never reuse a nonce with the same AES-GCM key. The code generates a fresh random nonce for every operation. Losing the encryption key makes old content unreadable.

15. SecureVault: policy plus short-lived grants

SecureVault is learned best as two stages: authorize, then redirect.

Stage 1: public access page

VaultAccessPage.tsx loads policy information, shows password/sign-in UI and calls vaultApi. VaultAccessService verifies the password, authenticated user or allowlist.

Stage 2: grant

VaultGrantService creates a short-lived JWT containing subject, slug, purpose, type, ID, issued/expiry time, issuer and audience. The redirect validates every claim before decrypting the destination.

Authorization lesson: A grant is proof that a recent policy check succeeded. It is short-lived and bound to one resource rather than being a permanent download/redirect secret.

16. ShareVault from upload to download

Owner-side modules

ShareVaultPage.tsx collects a file and policy. useShares.ts controls state. shareVaultApi.ts sends multipart FormData. shares.py accepts the upload and calls ShareVaultService.create.

Creation inside the service

  1. Validate extension, size and signature.
  2. Validate password/allowlist/expiry/limit.
  3. Create random slug and storage key.
  4. Encrypt and upload through the storage adapter.
  5. Create a direct QR to the Vercel access page.
  6. Create the MongoDB metadata record.
  7. If a later step fails, delete already-uploaded bytes (rollback).

Recipient-side modules

SharedFileAccessPage.tsx loads public policy, obtains a grant and downloads. The backend rechecks policy identity, reads encrypted Blob bytes, decrypts in memory, atomically consumes a download and records history.

Practice: Trace one public share and one private share. Write which requests require authentication and why.

17. File validation and secure responses

Validation examples

  • PDF must begin with %PDF.
  • Office/O​​DT containers must begin with ZIP marker PK.
  • Images are opened and verified with Pillow.
  • MP4/MOV checks ftyp; WebM checks its signature.
  • Text/CSV must decode as UTF-8.

Response headers

HeaderPurpose
Content-Disposition: attachmentDownloads with a safe original/generated filename.
Cache-Control: no-storeAvoids caching decrypted/private bytes.
Referrer-Policy: no-referrerPrevents grant URL leakage.
X-Content-Type-Options: nosniffStops browsers guessing an unsafe content type.
Boundary lesson: Extension/signature checks reduce obvious abuse but are not antivirus scanning. Code and UI should never claim stronger protection than implemented.

18. BulkForge: reuse, jobs and partial success

Modules in order

  1. BulkForgePage.tsx — upload, format selection and job table.
  2. useBulkJobs.ts — polling and actions.
  3. bulkForgeApi.ts — multipart/API calls.
  4. infrastructure/bulk/parser.py — CSV/XLSX rows to QR request schemas.
  5. BulkForgeService — progress and row loop.
  6. QrGeneratorService — reused individual generation.
  7. BulkZipStorage — safe ZIP names and bytes.
  8. BulkJobRepository — persistent job state.

Why background tasks?

The create endpoint responds with HTTP 202 and schedules processing. The frontend polls status instead of holding one long upload request. For very large production workloads, a real queue/worker would replace in-process background tasks.

Partial result pattern

Each row is isolated in a try/except. Valid rows continue, failed rows add bounded messages, and the final status can be partial. This is a useful design for imports.

19. Dashboard aggregation

A dashboard is not a single table. DashboardRepository queries multiple collections and returns a summary. DashboardService presents it through the endpoint. The frontend hook loads it and the page maps values to stat cards and lists.

Learning aggregation

  • Count close to the database instead of loading all objects.
  • Restrict every aggregation by owner ID.
  • Keep recent lists bounded.
  • Record lightweight download events rather than duplicating full files.
  • Render honest empty states.
Practice: Choose one Dashboard card. Trace its number back to the exact repository query and collection.

20. Notifications and Brevo email

Event creation pattern

Feature code calls NotificationService.notify(user_id, event_type, category, severity, title, message,...). The service checks category preferences, creates an in-app record and optionally sends email.

Delivery adapter

BrevoEmailSender uses httpx.AsyncClient to POST sender, recipient, subject, text and branded HTML. It escapes title/body before HTML insertion. If no Brevo key exists, dependency injection can select local SMTP for development.

Why notification failure does not fail the main action

Email is a secondary side effect. A successful ShareVault download should not be reversed because the email provider is temporarily unavailable. Failures are caught and logged.

Reliability lesson: Separate the primary transaction from optional notifications. In a larger system, an event queue would improve retry and delivery guarantees.

21. Profile and password rotation

ProfilePage.tsx contains separate display-name and password workflows. ProfileService verifies business rules and calls User/Session repositories.

Password rotation sequence

  1. Verify the current password hash.
  2. Validate and hash the new password.
  3. Update the user and increment token version.
  4. Revoke all refresh sessions.
  5. Clear the refresh cookie.
  6. Frontend returns to login.

This feature teaches that changing a password is not only updating one database field; existing credentials must be invalidated.

22. Admin and audit features

Module chain

AdminPage → useAdminDashboard → adminApi
 → admin endpoints (AdminUser dependency)

Business rules in the service

  • An admin cannot disable/change their own access accidentally.
  • The final active administrator cannot be removed.
  • Role/status changes revoke target sessions and invalidate tokens.
  • Every sensitive change creates an audit event.
Layering lesson: These rules belong in the service, not only in disabled frontend buttons, because API callers can bypass the page.

23. Internationalization and theme

i18n modules

Theme modules

24. Database repositories and indexes

Repository pattern

A repository translates domain operations into MongoDB queries. Example: find_owned(id, user_id) includes both identifiers, so ownership is part of the query rather than checked later.

Why indexes are created at startup

db/mongodb.py defines unique and compound indexes for emails, slugs, owner/time lists, analytics and unread notifications. Indexes turn common filters/sorts from collection scans into efficient lookups.

Repository learning sequence

  1. Read a simple find_by_id.
  2. Read create and document-to-model conversion.
  3. Read owner-filtered pagination.
  4. Read atomic update/consume logic.
  5. Finally read analytics aggregation pipelines.

25. Error handling and observability

Request IDs

Middleware accepts or generates X-Request-ID, adds it to response headers and structured logs. A frontend error can be matched with a backend log without exposing stack traces.

Error categories

TypeResponse
Application ruleSpecific safe code/message and appropriate status.
Pydantic validation422 with validation details.
Authentication401 and Bearer challenge.
Unexpected exceptionGeneric 500; full exception only in server log.

Structured logging

Logs include timestamp, level, logger, message and contextual fields such as path, status and duration. This is easier for hosted log search than arbitrary print statements.

What .venv teaches

A virtual environment isolates Python packages. requirements.txt declares dependencies, and Render rebuilds them in a clean environment instead of copying the developer’s virtual environment.

Environment-aware adapters

The same source runs locally and in production because Settings supplies URLs/secrets and dependency injection chooses local or cloud storage. This teaches the twelve-factor principle of external configuration.

31. Final coding principles learned

Separation of concerns

Pages display, hooks orchestrate, APIs transport, endpoints adapt HTTP, services decide, repositories persist and infrastructure integrates.

Single responsibility

PayloadBuilder creates payload syntax; Renderer draws; Storage stores. Small focused modules are easier to test.

Dependency inversion

Services depend on behavior, while dependency injection chooses local/cloud implementations.

Defense in depth

Frontend guards, backend authorization, validation, encryption, safe headers and private storage reinforce one another.

Data ownership

Owner filters belong in database queries, not only after retrieval.

Honest limitations

SafeScan is heuristic, free hosting sleeps and unauthenticated email domains have deliverability limits.

Test behavior

Fake external clients but assert the request, data transformation and side effects.

Debug evidence

Inspect actual QR contents, response codes, logs, environment names and deployed commit IDs.

Conclusion

IntelliQR is best understood as a collection of small, testable modules connected into larger workflows. Begin with types and pure functions, follow one request through every layer, and only then read the large page or service as a whole. That method can be reused for almost any full-stack project.
